# 钱本 · QianBen

**不用记账的账本。**

钱本是一套个人财务状态引擎：从支付通知、账单和用户输入中整理证据，恢复真实经济事件，再用确定性的复式记账规则维护资产、负债、消费和现金流。证据不足时保持待确认，判断错误时通过可追溯的冲销与修正处理。

> 当前处于需求与架构设计阶段。仓库已包含 PRD、技术设计和架构审查记录，尚未提供可运行的 App 或后端服务。项目由个人开发维护。

## 为什么做钱本

支付通知可能重复、延迟、缺字段；微信和银行也可能各自描述同一笔支付。钱本将“重复消息”和“同一经济事件”分开处理，目标是在不依赖银行实时 API 的情况下，减少逐笔手工记录，同时明确账本的覆盖范围与不确定性。

- **证据优先**：原始观察、接受的解释和正式账务分别保存。
- **确定性入账**：AI 可辅助解释，正式账务必须经过规则与会计约束。
- **可追溯纠错**：历史账务通过冲销和修订调整，不静默覆盖。
- **三套视图**：会计费用、生活消费和现金流分别计算，信用卡还款不重复计消费。
- **诚实展示**：待确认、暂记和未覆盖账户明确可见；借贷平衡不代表已经和银行对账。

## 技术架构

Android 客户端使用 Kotlin，后端使用 Go 模块化单体，API 与异步 worker 共用领域逻辑，PostgreSQL 作为正式账本的唯一写入权威。

```mermaid
flowchart LR
    A[通知 / CSV / 手动输入] --> B[版本化证据]
    B --> C[事件识别与待确认]
    C --> D[确定性会计核心]
    D --> E[PostgreSQL 正式账本]
    E --> F[会计 / 消费 / 现金流]
```

| 部分 | 选型与职责 |
|---|---|
| Android | Kotlin、Room、NotificationListenerService、WorkManager；本地筛选、持久化、上传与缓存 |
| API / Worker | Go、net/http、pgx、sqlc；证据接收、领域命令、可靠任务 |
| 正式账本 | PostgreSQL；复式记账、版本约束、原子修复、事务 Outbox |
| 报表 | 三套视图按同一账本版本发布，支持重建 |

这些是已选定的设计方向，具体依赖版本在工程初始化时锁定。完整事务协议见技术设计文档。

## MVP 范围

- 统一起始时点的期初余额、CNY 正式账户。
- 经真机验证的通知入口，以及明确格式的 CSV 导入、手动输入。
- 证据去重、事件关联、账户与支付通道区分、复式记账。
- 未知用途资金变动先暂记，提供用户确认与修订。
- 信用卡消费与还款、退款、转账两端、报销、用户确认的资产购置与原值。
- 三套财务视图，以及基础认证、数据隔离、删除与恢复。

完整银行对账、固定资产折旧与处置、市场估值和复杂 AI 识别按后续版本推进。通知可读性和覆盖率仍待真机验证，不能把开启权限当作交易已完整采集。

## 开发顺序

1. 做 Android 通知真机实验，收集脱敏账单样本，明确可用入口。
2. 实现账户、期初余额、手动消费及暂记纠错的账务闭环。
3. 接入本机证据队列、上传 ACK、CSV 和确定性解析。
4. 完成用户确认、跨来源关联、信用卡、退款与转账场景。
5. 验证原子修复、报表重建、故障恢复、安全及删除。

当前仓库没有启动命令；后端和 Android 工程落地后，会补充环境要求、迁移与运行步骤。

## 个人开发约定

`main` 保持可审阅的稳定版本，功能分支使用 `codex/<topic>`。涉及业务口径的变更先更新 PRD，涉及事务和数据模型的变更同步更新 TDD。一个提交围绕一个明确目的，提交说明记录变更原因和实际验证结果。

通知正文、真实账单、账号、数据库备份和密钥不提交到仓库；测试样本使用脱敏或合成数据。待验证的能力明确标注，不将设计要求写成已经实现的功能。
